# Design — 002 Store tasks in Postgres instead of memory

## Decisions

- Tasks live in one Postgres table `tasks`, reached with **psycopg 3** (`psycopg[binary]`, sync API; the binary wheel bundles libpq, so the slim runtime image needs no system package). The sync API keeps the existing sync handlers and the thread-pool model from 001. ADR: [ADR-001](../../adr/001-postgres-task-persistence.md).
- **One connection per request**, no pool. `psycopg.connect(DATABASE_URL, connect_timeout=2, options="-c statement_timeout=3000", application_name="taskboard15-api")`. Reason: reconnecting after an outage is then trivially immediate (AC-002.6, "without a restart"), and the timeouts are exactly the contract's (connect 2 s, statement 3 s, so a failing request answers `503` well within 5 s, AC-002.5). A pool's background reconnect backoff would delay recovery and blur the 5 s bound; at this service's load the per-request connect cost (a few ms in-cluster) does not matter. A pool is a later, local change behind `Database.connection()`.
- **Schema created by the service, idempotently, at first use** (no migration tool). `TaskStore.ensure_schema()` runs, inside one transaction, `SELECT pg_advisory_xact_lock(7316002)` and then `CREATE TABLE IF NOT EXISTS tasks (...)`. The advisory lock serialises two replicas starting at once against an empty database, because a bare `CREATE TABLE IF NOT EXISTS` can still fail with a unique violation on `pg_type` when two sessions race (AC-002.4). A per-process flag (guarded by a `threading.Lock`) skips the DDL once it succeeded. It is called by `/ready` and before every store operation until it has succeeded, so a service that started while the database was down creates the schema when the database appears (AC-002.6). A migration tool (Alembic) comes with the first schema change that is not additive.
- **Creation order** is an internal identity column `seq` (`ORDER BY seq`), never exposed (spec note, system A1). `id` stays `str(uuid.uuid4())` generated by the store, as in 001, stored in a `uuid` column, so ids look exactly as before.
- **Database unavailable = one exception.** `Database.connection()` turns `psycopg.OperationalError` (covers connection refused/timeout and `QueryCanceled` from the statement timeout) and `psycopg.InterfaceError` into `DatabaseUnavailable`; an app-level exception handler answers `503 {"detail": "database unavailable"}`. Inserts run in a transaction, so a failed `POST` stores nothing (AC-002.5). Other database errors are bugs and stay `500`.
- **`DATABASE_URL` is the only new config** (spec note; the `PG*` variables are ignored). Unset or empty means "no database": the app still starts, `/health` is `200`, `/ready` and `/tasks` answer `503`; a `database_url_missing` warning is logged once at startup. Reason: a missing secret then shows up as a not-ready pod, not a crash loop, and template tests that import `main.app` without a database keep working. The URL is never logged (it carries the password); failures log `database_unavailable` with the exception class name only.
- **`/ready` with a 1 s budget.** libpq treats connect timeouts below 2 s as 2 s, so `/ready` is an `async def` that runs the sync check (`ensure_schema()` then `SELECT 1`) via `asyncio.to_thread` under `asyncio.wait_for(..., timeout=1.0)`; a timeout or `DatabaseUnavailable` answers `503 {"status": "not ready"}`. The abandoned thread ends by itself within the 2 s connect timeout. `/health` does not touch the database.
- **App factory.** `main.py` gains `create_app(database_url: str | None = None) -> FastAPI` (`None` reads `DATABASE_URL` from the environment); `app = create_app()` stays the module-level ASGI target, so the Dockerfile `CMD` is unchanged. Two `create_app(url)` objects against one database are the in-process form of two replicas (AC-002.3, AC-002.4).
- Departs from note "The 422 validation and the existing criteria AC-001.1 to AC-001.5 and AC-001.7 stay unchanged": a `title` containing U+0000 is now rejected with `422` naming `title` (`value_error`). Postgres `text` cannot hold NUL, so the only alternative is a `500` for an input the 001 validation accepted; every other validation rule is unchanged.
- No gitops task: the system plan's gitops part already wires the `postgres` resource (`DATABASE_URL`) and 2 replicas in dev for this component (spec, "Provided by the system"). Port, probe paths and image are unchanged.

Signatures:

```python
# db.py
class DatabaseUnavailable(Exception): ...

class Database:
    def __init__(self, url: str | None) -> None: ...
    @contextlib.contextmanager
    def connection(self) -> Iterator[psycopg.Connection[Any]]: ...
        # url None/"" -> raise DatabaseUnavailable
        # psycopg.connect(url, connect_timeout=2, options="-c statement_timeout=3000",
        #                 application_name="taskboard15-api"); closes on exit;
        # OperationalError | InterfaceError -> DatabaseUnavailable (from err)
    def ping(self) -> None: ...   # SELECT 1; raises DatabaseUnavailable

# tasks/store.py
class TaskStore:
    def __init__(self, db: Database) -> None: ...
    def ensure_schema(self) -> None: ...      # once per instance; advisory lock + CREATE TABLE IF NOT EXISTS
    def create(self, title: str, due_date: datetime.date | None) -> Task: ...   # ensure_schema(); INSERT in a transaction
    def list(self) -> list[Task]: ...         # ensure_schema(); SELECT id, title, due_date FROM tasks ORDER BY seq

# main.py
def create_app(database_url: str | None = None) -> FastAPI: ...
app = create_app()
# app.state.db: Database; app.state.task_store: TaskStore
# @app.exception_handler(DatabaseUnavailable) -> JSONResponse(503, {"detail": "database unavailable"})
# async def ready() -> 200 {"status": "ready"} | 503 {"status": "not ready"}
```

## Contract

Unchanged from spec 001 except the status codes below; the spec's Contract section is binding and repeated here in short. All bodies `application/json`.

### `POST /tasks`

- Request: `title` string, required, 1 to 200 code points, at least one non-whitespace character, no U+0000, stored as sent; `due_date` `"YYYY-MM-DD"` or `null`/absent, real calendar date, past allowed. Unknown fields (including `id`) ignored.
- `201`: `{"id": "<opaque string>", "title": "<as sent>", "due_date": "YYYY-MM-DD" | null}` (AC-002.7).
- `422`: FastAPI standard body `{"detail": [{"loc": ["body", "<field>"], "msg": "...", "type": "..."}, ...]}`, field is `loc[1]` (`title` or `due_date`); nothing stored. Validation runs before any database access, so invalid input answers `422` even while the database is down.
- `503`: `{"detail": "database unavailable"}` within 5 s; nothing stored (AC-002.5).

### `GET /tasks`

- `200`: bare JSON array of all tasks, creation order oldest first, each exactly as returned by its `POST`; `[]` for an empty database (AC-002.1, AC-002.2, AC-002.3).
- `503`: `{"detail": "database unavailable"}` within 5 s (AC-002.5).

### Probes

- `GET /ready`: `200 {"status": "ready"}` when the schema exists (created if needed) and `SELECT 1` answers within 1 s; else `503 {"status": "not ready"}`. Recovers without restart (AC-002.6, AC-002.4).
- `GET /health`: `200 {"status": "ok"}`, never touches the database (AC-002.6).

### Configuration

| Variable | Default | Meaning |
|---|---|---|
| `DATABASE_URL` | unset | libpq URI, e.g. `postgresql://user@host:5432/db`; unset means not ready and `503` on `/tasks` |

## Data

```sql
CREATE TABLE IF NOT EXISTS tasks (
    seq      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- creation order, internal
    id       uuid   NOT NULL UNIQUE,
    title    text   NOT NULL,
    due_date date   NULL
);
```

Created by `TaskStore.ensure_schema()` under `pg_advisory_xact_lock(7316002)`. No data migration: the in-memory tasks of 001 are not carried over (they never survived a restart).

## Test seam

- Tests need a real Postgres. The dev environment gets the devbox package `postgresql` (provides `pg_ctl`/`initdb`) and the dev dependency `pytest-postgresql`; CI's `devbox run test` gets both through devbox. No Docker needed.
- `tests/conftest.py` belongs to the acceptance tests (testers): a session-scoped `postgresql_proc` from `pytest_postgresql.factories.postgresql_proc(executable=shutil.which("pg_ctl"))`, a `pg_url` fixture building `postgresql://<user>@<host>:<port>/<dbname>` from it, and `task_client` returning `TestClient(create_app(database_url=pg_url))` after `DROP TABLE IF EXISTS tasks` (an empty database each test, which also exercises schema creation). The `client` fixture stays the module app without a database.
- Restart (AC-002.1): a second `create_app(pg_url)` against the same database. Two replicas (AC-002.3, AC-002.4): two `create_app(pg_url)` objects; concurrent start = calling `/ready` on both from two threads at once on a dropped table.
- Database down (AC-002.5, AC-002.6): stop the `postgresql_proc` executor (`.stop()`) and start it again (`.start()`) on the same port and data directory; the same app object must answer `503`, then `200` after the start. A never-reachable database is `create_app("postgresql://u@127.0.0.1:1/x")`.
- The 001 acceptance tests for AC-001.6 and AC-001.8 are replaced by AC-002.2 and AC-002.1 (AC-001.8's "fresh store is empty after restart" is now false by design); the testers drop them. The 001 tests for AC-001.1 to AC-001.5 and AC-001.7 run unchanged on the new `task_client`.
- Smoke: a read-only `GET /ready` → `200 {"status": "ready"}` check is the deployed proof the database is wired (staging and prod); the 001 smoke tests stay.
